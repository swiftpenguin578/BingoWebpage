# Architecture

Owns data invariants, calculations, architecture and the authentication/authorization mechanism. Product behaviour is in [PRODUCT.md](PRODUCT.md), UI rules in [UI.md](UI.md), operations in [OPERATIONS.md](OPERATIONS.md).

## 1. Architecture and structure

- The application is one portable ASP.NET Core monolith running on a small Hetzner VPS.
- Stack: .NET 10 LTS, ASP.NET Core, server-rendered Razor Pages/components, small focused JavaScript modules, SignalR for live board/review updates, EF Core + Npgsql, PostgreSQL, Cloudflare R2 for evidence and durable images, Docker Compose, Caddy, images in GHCR, automated off-site PostgreSQL backups.
- Not used: microservices, Kubernetes, a separate SPA, Redis, a message broker, Elasticsearch, a separate worker server, multiple replicas, managed realtime services. Reconsider only on measured usage or operational problems.
- Projects: `Bingo.Web` (pages, endpoints, authentication, hubs, static assets), `Bingo.Application` (workflows; interfaces for storage, time, notifications), `Bingo.Domain` (entities, transitions, calculations, errors), `Bingo.Infrastructure` (EF Core, migrations, R2, password/token handling, scheduling, the operator catalogue import, which is not an Admin UI workflow). Tests: Domain, Application, Integration, Browser.
- Dependency direction: Web and Infrastructure → Application → Domain. Domain has no dependency on ASP.NET, EF Core, PostgreSQL, R2 or Hetzner.
- Domain/application services own lifecycle, eligibility, privacy and cross-record rules; Razor, JavaScript and database triggers never replace them.

## 2. Web rendering and interaction

- Pages are server-rendered Razor by default; basic operations and navigation work without JavaScript.
- JavaScript is used only where it materially improves interaction (board transitions, tile drag-swap, upload preview, drawers, responsive navigation). Every important mutation goes through an authenticated server endpoint with server-side validation.
- Schedule fields post local `yyyy-MM-ddTHH:mm` strings from the shared picker; the server is the authority for clock changes and five-minute steps.
- The Teams page embeds its state as `<template data-draft-state>`, because shell navigation accepts only page/shell scripts (a JSON script would force full loads).

### Admin in-page navigation

- The Admin shell navigates in place: shared dirty guard, target-page skeleton, normal HTML fetch, then swap of content, title, breadcrumb, navigation and page script; Back/Forward work; a failed load offers Try again. Unexpected responses and old-layout targets fall back to a full load. One site-wide setting, `AdminUi:InPageNavigation` (default true), disables swaps; false keeps the dirty guard with full loads. Repeated event switches leave no stale work.
- A temporary skeleton may show before a full-load fallback; the address bar changes only after a successful swap.
- Page-script contract: a same-origin ES module `<script type="module" data-admin-page-script>` exporting async `init(root, ui)` and `dispose()`; nothing initialises at module top level; `root` is the `[data-page-region]` element and `ui` is `window.AdminUI`. Drafts register via `registerDraft(owner, {isDirty, discard, isPending})` or `trackForm(form)`. `dispose` aborts requests, unregisters drafts, removes listeners, timers and connections, and ignores async work completing after disposal. The shell disposes the old page (awaiting layer closure) before fetching/swapping and before the next page initialises. Page CSS links carry `data-admin-page-style`.
- A registered dirty draft may supply `confirmLeave()` for a page-specific uncertain-save warning; the shared guard still refuses navigation while a save is pending and owns sidebar, switcher, breadcrumb and history transitions.
- Filter/search URL updates use `AdminUI.setUrl` (history replace); opening a record passes `{record:true}` (push). Query schemas validate values and omit defaults.
- Pages supply `<template data-page-loading-template="<kind>">` for their loading composition; the shell remembers it and otherwise uses a generic skeleton. A discarded draft is never stored in browser history.
- Page stylesheets are family-scoped with zero-specificity `:where([data-page-family])`; loaded page and skeleton carry a fixed PageFamily key. Destination CSS is loaded and awaited before its skeleton/swap shows (the current page stays if it is not ready within 150 ms); an unknown family uses the generic skeleton; old styles are removed only after the old content; stale links reload; errors fall back to a full load.

### Admin fetch contract

- Pages use `AdminFetch.request(url, {expect, draft, labels, readback, …})` for saves and reads. Field-keyed draft values plus localized labels populate the session notice; `readback` selects uncertain-outcome wording. Non-2xx is "unknown" with its status, classified before HTML/session checks; only a successful HTML response where JSON was expected means a lost session.
- Handler error, session lost, refused and unknown are handled separately. An unknown write requires the page's readback contract and is never resent automatically. Only an explicit same-page PRG destination may pass via `allowRedirectTo`, and the page still validates the returned data.

## 3. Persistence and conventions

- PostgreSQL stores event configuration, signup and waiting list, teams/rosters/picks, catalogue and snapshots, boards/tiles/requirements, submission metadata and review history, derived progress caches, accounts/access, audit, asset metadata and event-linked notification metadata (for hidden-event filtering). Screenshot binaries are never stored in PostgreSQL.
- EF Core provides migrations, transactions, optimistic concurrency tokens, constraints and typed queries; database constraints and indexes are used where needed. Competitive invariants never rely only on UI or application checks.
- Competitive records, transitions, memberships, assignments, submissions, evidence, board approvals, official results and access changes are append-only or versioned.
- Records that influenced an event are disabled, withdrawn, rejected, reversed or archived, never permanently deleted.
- Retiring a feature removes its future authority before any historical storage is deleted. Harmless enum values, columns and FKs stay for emergency actors, accountless participants, old formation types, departures/replacement links, legacy resubmission predecessors, review resolutions/manual corrections, legacy Finalized events and old planning fields. Historical records stay readable without reactivating retired commands.
- Every record has a stable id, `created_at` and `updated_at`; disable/archive uses `active`/`archived_at`.
- All timestamps are stored as timezone-aware instants; events also store a display timezone (normally Europe/Copenhagen).
- User-facing ordering never depends on insertion order; it uses an explicit position, sequence, signup time or name.

## 4. Data model

- Entity classes live in `src/Bingo.Domain` (one folder per domain); EF Core mapping lives in `src/Bingo.Infrastructure/Persistence/Configurations` and `ApplicationDbContext.OnModelCreating` (`src/Bingo.Infrastructure/Persistence/ApplicationDbContext.cs`). These are the authority for fields, types and relationships; this section records only rules the code alone does not make obvious.
- Events own competitive data: players, teams, boards, submissions, rankings and draft records are event-scoped. Published events keep snapshots of the catalogue values they used.

### Event

- Entity: `BingoEvent`. Its times cover the scheduled signup opening (when automatic), actual signup opening/closing, signup closing, an optional informational draft time, scheduled start and end, the internal derived submission cutoff, actual start, the authoritative actual/effective end, actual submission closure and finalization time.
- States: DRAFT, SIGNUP_OPEN, SIGNUP_CLOSED, LIVE, AWAITING_FINAL_REVIEW, FINALIZED, ARCHIVED, CANCELLED, DISCARDED (`EventState`).
- An incomplete DRAFT needs only a valid name, unique slug, timezone, creator and creation time. Schedule, signup, capacity and planning fields become required only at the readiness gate of the transition that uses them.
- Description may be null in a private draft and is required before signup publication. Events have no event-level banner/artwork field or banner asset.
- `first_public_at` records the first intentional exposure of any event-owned public page and is never cleared. Slugs are permanent.
- Schedule fields are nullable in a draft. Signup publication requires `signup_closes_at`, `event_starts_at` and `event_ends_at`. `signup_opens_at` is used only for scheduled opening (retained as history otherwise); `actual_signup_opened_at` records the actual opening and becomes the effective lower bound (manual opening does not overwrite `signup_opens_at`); `draft_at` is optional and informational. Invariant: `effective_open = actual_signup_opened_at ?? signup_opens_at` and `effective_open < signup_closes_at <= event_starts_at < event_ends_at <= submission_cutoff_at`.
- `scheduled_signup_opening_enabled` is compatibility state, not an Admin control: a future opening timestamp schedules the opening; a manual action supersedes the matching scheduled transition; the legacy disabled/overdue exception is preserved. One `ScheduledSignupOpeningAttempt` exists per event and boundary; the transaction plus uniqueness make scheduled/manual races idempotent; readiness is always rechecked; old warning acknowledgements grant nothing.
- `ScheduledEventStartAttempt` records every scheduled start check, including blocked ones (scheduled time, attempt time, started flag, blocker codes, resolution time).
- `EventStateTransition` records every lifecycle change (from/to, actor, time, scheduled flag); a reason is required for exceptional or backward transitions.
- DISCARDED is a terminal tombstone, allowed only when no participant, team, event-scoped access, submission or evidence exists. Setup records (boards, tiles, requirements, questions, planning) may be removed in the discard transaction. The tombstone keeps id, name, slug, creator, discard actor and timestamps; the slug stays reserved; discarded events are excluded from Admin and public listings.
- Hidden is not an `EventState`: `is_hidden = hidden_at != null`, with `hidden_by` (a Super Admin) and a mandatory `hidden_reason`. Hiding is allowed only in AWAITING_FINAL_REVIEW, FINALIZED or ARCHIVED and changes no lifecycle state or relation. Hide and Restore are audited mutations, not transitions; Restore clears only those three fields.
- `event_creation_operations`: PK `(actor_account_id, request_id)`, stores the trimmed name and timezone and a unique `event_id`; immutable; commits with the event aggregate and creation audit; restrictive FKs survive rename/quarantine/discard. Payloads compare ordinally (timestamps and slug are not identity); a new key is a new operation; a validation failure leaves no row.
- `events.placement_rule` is immutable: 0 = `LegacyScoreTimeThenEhb`, 1 = `CreditedEhbThenScoreTime`. There is no database default; `EventCreationService` inserts 1, historical import and fixtures pass 0 explicitly, transient copies keep the source rule; the rule is never inferred from dates. The domain has no mutator and EF rejects changes. Each new official snapshot records the rule in its calculation inputs.
- Board planning team size (`ExpectedTeamSize`) only estimates board EHB; it never seeds draft teams, constrains rosters or represents completed structure. No expected team count is used.
- Wise Old Man (WOM) provenance and credential/write capability are separate: unknown provenance can never gain delete permission, external ID-only links stay read-only, protected credentials never appear in output or Audit.
- At most one WOM integration-state record per event holds: competition identity plus validated title/start/end; latest generation with completeness/error; last request/success times; separate normal-slot and retry due times (normal slots are UTC-anchored to the retained `actual_started_at`, first slot at +1 h; a missing anchor leaves normal due NULL, no rolling fallback); retry count; opaque lease owner/expiry; request-budget diagnostics; end-update status (`NotRequired`, `Pending`, `Succeeded`, `Rejected`, `CouldNotUpdate`, stored by name, never renamed) with UTC target/requested times and a sanitized rejection code.
- Each sync attempt snapshots the generation id, competition id and a fingerprint of the current unreleased PLAYING assignments. Cached per-character activity rows (event, participant, character, gained EHB, fetch time) belong to that generation; alt and released assignments are excluded.
- Persisted WOM refresh skip reasons keep names and numbers and are never reused: `EventUnavailable=0`, `EventNotInFinalReview=1`, `IncompleteEventWindow=2`, `NoCompetition=3`, `RefreshInProgress=4`, `RetryDelay=5`, `NotDue=6`, `ServiceUnavailable=7`, `EndWindowUnmatched=8`, `EndCouldNotBeUpdated=9`. `CalculationInputsJson` reads both old string and numeric forms. A fallback publication records `Skipped`/`EndCouldNotBeUpdated` and keeps the pre-end cache with its timestamps (no fresh values or zeroes).
- Managed WOM: the competition link is the source identity. A management record is created only after explicit Create or explicit protected-code adoption. It stores the link, encrypted versioned code, managed-field scope, status, last local/remote fingerprints, acknowledged roster, version and the permanent `actual_started_at` cutover. The code is never cleartext and never in DTOs, TempData, logs, exceptions or payloads. ID-only links have no write capability; adoption does not change External provenance or authorize deletion. Replacement/disconnect retires the connection, removes the credential and current receipt and keeps operation history; re-adoption rebinds with a new code only; replacement resets end-update state.

### Global public content

- One non-event Rules document: a well-known singleton id, body, `version` (optimistic concurrency), `updated_at`/`updated_by`. Edits are audited automatically with no reason and no notifications; it is not a readiness input. (No `GlobalRulesDocument` entity exists in code yet; the retired per-event `BingoEvent.PublicRules` field is not this document.)

### Signup

- `SignupForm`: one active form per event; historical question definitions remain. `first_response_at` is set by the first accepted or imported response and never cleared.
- `SignupQuestion`: `public_on_signup_board` is fixed true for participant-facing questions. Types TEXT, NUMBER, YES_NO, SINGLE_CHOICE, ACCOUNT; account answer role PLAYING / INFORMATIONAL (ACCOUNT only).
- `SignupQuestionCreationOperation` (one per committed add): globally unique `request_id`, actor, event, SHA-256 of the canonical requested shape (including `expectedFormVersion`) and `question_id`. It commits atomically with the question, audit and form-version advance; actor/event FKs are restricted; the question id is kept without a cascading FK; replay never recreates a deleted field; Development reset clears it with event data. No backfill, failed-write receipts or expiry.
- Draft start freezes question metadata. Delete-then-create gives a new stable key and never rewrites deleted answers. Deletion uses an internal tombstone (references stay valid), removes answer rows and releases current optional assignments in one transaction under the event lock, advancing form and participant versions; repeated deletion is harmless. Draft-locked and later records are never rewritten.
- `EventParticipant` is one person's participation in one event, not the login identity or an OSRS character. `account_id` is nullable only for imported/external records; `(event_id, account_id)` is unique when `account_id` is not null.
- Signup status CONFIRMED, WAITING_LIST, WITHDRAWN. Signup source WEBSITE, CSV_IMPORT (retained historical value; CSV import is retired), ADMIN_CREATED.
- Payment is a private boolean, default unpaid.
- `SignupAnswer` keeps `question_label_snapshot` so meaning survives edits; `value` is null for ACCOUNT answers, which use `osrs_character_id`. An answer row is not guaranteed per question/participant: team, roster, draft and Admin views load answers with left-join/optional semantics and render missing values without throwing.
- `OsrsCharacter`: `normalized_name` is trim + case-insensitive only (no spelling rewrite) and unique. Typed new or renamed names must match `RsnRule` (1–12 letters, digits, spaces, `-`, `_`); which flows also check Wise Old Man is in PRODUCT.md §3. Stored names are never re-validated; there is no ownership validation. A character may link to many accounts globally but has one participant assignment per event.
- `AccountOsrsCharacter` is a trust-based link (`unlinked_at` hides without deleting; personal label, sort order, preferred, `saved_ehb`). `(account_id, osrs_character_id)` is unique; at most one preferred link per account; several accounts may link one character; a link grants no authority, ownership or reservation.
- `saved_ehb` belongs to the link (a borrower's edits do not affect others). Saving a regular answer updates the default and snapshots the event EHB independently; later `saved_ehb` edits never rewrite event assignments; alts ignore it. My accounts stores only the numeric default (no source/fetch metadata), so reusing it later records MANUAL; only a fresh signed lookup submitted and verified with a signup creates a WISE_OLD_MAN snapshot.
- Name normalization may flag shared characters for Admin awareness but never blocks a valid global link, creates a person identity, implies ownership or links name changes across bingos; it does block a second assignment in the same event. Character association never merges participants or grants authority; evidence and WOM resolve through the unique event assignment.
- `EventParticipantCharacter`: `ehb_snapshot` and `ehb_source` are required for PLAYING and EHB is null for INFORMATIONAL. Partial unique `(event_id, osrs_character_id) WHERE released_at IS NULL`; participant and assignment `event_id` must match via a relational constraint. Confirmed and Waiting participants both hold assignments; pre-draft withdrawal/removal releases them (history kept) so the character can be reacquired; the same character may be assigned in other events.
- Event role PLAYING/INFORMATIONAL is set by the Account question, independent of the personal label. At least one current PLAYING assignment is required to complete signup. Each PLAYING assignment has its own EHB snapshot. INFORMATIONAL never takes part in swaps, evidence credit or WOM sync.
- The primary Playing account is the mapping of the first/protected Playing question (`SignupSystemField.PrimaryRegularAccount`), not a second primary flag; it is automatically the initial active account. Exactly one primary Playing assignment supplies draft EHB (others never add to it).
- EHB source MANUAL, WISE_OLD_MAN, IMPORT, ADMIN_CORRECTION. Switching the primary preserves per-account snapshots; a fetched value records WISE_OLD_MAN plus `ehb_fetched_at`, editing it changes the source to MANUAL; the event snapshot is authoritative after signup closes.
- `EventParticipantCharacterSwap` is append-only history deciding the one active, drop-eligible character at any instant (`reason` only on historical rows). Initial activation is the selected primary. While Live a participant swaps among their own frozen Playing assignments, effective at authoritative server time (PostgreSQL precision) and serialized with submission attribution. There is no pending next-minute swap, backdating or Captain/Admin on-behalf switching; exactly one account is active; history and evidence snapshots never change.
- Moving a participant Confirmed→Waiting keeps their event-character reservations, preserves the rest of the queue order, appends them, atomically promotes the next pre-existing eligible waiter and keeps membership/leadership history while ending current authority. With no eligible waiter or an open place the request fails without mutation.
- Question-free Admin Add requires an existing active website account, unique event ownership, at least one Playing assignment, non-negative supported EHB, configured slot limits and exactly one primary; payment is saved atomically; captain is false; unrelated unanswered questions stay absent (no fabricated answers).
- Admin event-only account corrections never change `AccountOsrsCharacter` links/defaults or rename a shared `OsrsCharacter`; reassignment resolves a character for this event while keeping assignment history and event uniqueness.

### Teams and draft

- Roster publication records its method: direct manual assembly (0/1 included team) or website draft (2+). No-draft is never inferred from the absence of active picks and pick/Running history is never fabricated; backfill only from reliable evidence (historical unknown is allowed). Original picks and earlier publication versions are preserved.
- `Team`: display name unique within the event; slug stable. `formation_type` (DRAFTED/PREFORMED) is historical compatibility only; image/affiliation fields are retained for history only. First-pick structural locks persist after Undo. There is no preformed/accountless workflow and no reopening of a finalized draft.
- `TeamMembership`: role PARTICIPANT, CAPTAIN, CO_CAPTAIN; source DRAFT_PICK, PREFORMED, ROSTER_REPLACEMENT. At most one active team membership per participant per event. `assigned_by_draft_pick_id` is null for manual members; manual assignments record structured source/action and the audit actor; pre-start corrections need no typed reason. Participants for an invited roster may be created directly without the public form.
- Historical departure/replacement memberships, `left_at` and ROSTER_REPLACEMENT links remain readable; ROSTER_REPLACEMENT is historical only and there are no new vacancy/replacement actions or notifications.
- `TeamMembershipRoleTransition` is append-only captain/co-captain history (previous/next role, effective time, actor).
- `TeamFocusMarker`: target kind TILE/ROW/COLUMN with mutually exclusive target fields, `focused`, version. Inspection choice is transient (no persisted record or global preference). Focus never affects snapshots, evidence, progress, ranking, finalization or history; it is read-only after the event ends; writes use optimistic concurrency and team-scoped invalidation so other teams cannot infer it.
- `DraftSession`: type SNAKE; states SETUP, RUNNING, FINALIZED; `first_pick_recorded_at` is retained after Undo/cancel; `requires_fresh_order`. PAUSED remains only as a readable legacy value of `DraftState`, not a control. `included_in_draft` is the only participation flag; `formation_type` never decides eligibility.
- `DraftTeamOrder` uses a 1-based `initial_position`; `DraftPick` uses 1-based overall/round/pick numbers and keeps undo fields.

### Accounts and access

- `Account`: `discord_user_id` nullable and unique; `public_username` with a case-insensitive unique normalized form; `login_username` only for emergency/legacy accounts; `password_hash` required after normal onboarding (emergency hashes grant nothing); authorization and password versions. Account type WEBSITE_ACCOUNT, EMERGENCY_CAPTAIN; global role USER, ADMIN, SUPER_ADMIN.
- `PasswordCredentialToken`: purpose PASSWORD_RESET / EMERGENCY_INITIAL_SETUP, `token_hash`, expiry/used/superseded times (rules in §9).
- `AccountDiscordIdentityTransition`: LINK/UNLINK/REPLACE with previous/new IDs and changed time/actor.
- `AccountEventAccess` scopes an account to a participant/team/role (CAPTAIN/CO_CAPTAIN). Normal captain access derives from the team membership role, never an OSRS name; captain history lives in `TeamMembershipRoleTransition`. Retained emergency accounts and access rows keep FKs, actor identity, username reservation and audit, but enabled/expiry/setup fields grant no authority; `expires_at` applies only to emergency/legacy access; there is no provisioning, token consumption, enabling, expiry worker or conversion.
- `PersonalNotification` (`personal_notifications`) is a durable recipient-specific destination/reminder, never the authoritative record. Indexes `(RecipientAccountId, ReadAt, CreatedAt)` and `(EventId, RecipientAccountId, CreatedAt)`; optional FK to the event; no universal recipient-transition uniqueness. `Route` must resolve under the recipient's current authorization; an empty route falls back to the notifications page. Event-linked notifications are filtered by `EventId` plus the visible-event predicate.
- Announcement and Drops NEW acknowledgements are independent of `PersonalNotification.ReadAt`. One unique account/event state (`DropAnnouncementAccountState`) stores the automatic-expansion cooldown and the last auto-announced approval ordinal; a claim needs an eligible approval beyond it and atomically advances only through the claimed snapshot together with the cooldown. Sparse unique account/submission records store banner and Drops acknowledgements; bulk acknowledgements apply under the ordinal snapshot boundary. Approval never fans out a record per recipient.

### Catalogue

- `BossActivity` covers bosses and broader activities (raids, skilling, Fortis Colosseum): name, image, category (boss/raid/skilling/minigame/other), active flag, efficient kills/completions per hour, external identifier, notes, connected drops. `team_size` is an integer ≥ 1, default 1, editable by every Admin beside completions/hour; it records the agreed team size and is informational.
- `CatalogueItem` holds item identity (fields in code). `SourceDrop` connects one item to one activity because rates are source-specific; it holds display rate, optional normalized probability, conditional-rate explanation (`rate_condition_note`), default EHB, data source, last-updated time and active flag.
- Each `SourceDrop` is one drop with one displayed rate/probability; conditional mechanics go in `rate_condition_note`; distinct real drops (e.g. Nid vs Nid (Destroy)) are separate records.
- `numeric_probability` is the final in-name chance per roll, paired with the activity's efficient completion rate for the same team size and strategy. `N x` records repeated rolls; fraction numerators are allowed; a raid item chance is entered with the purple chance included, never as an "Only after" rate. The effective chance is empty without a reviewed rate. Strategy details go in `rate_condition_note`, never into calculator exceptions.
- `probability_scope`, `conditional_on_parent`, `parent_probability` and `assumed_participants` are retained history columns: new writes are refused for every role, retained values stay readable and feed snapshots, and they never multiply a calculation. Luck may still apply retained parent mechanics while EHB ignores them; recheck for unexpected conditional records before changing this. Migrations never silently lose values or rewrite approved snapshots.
- `roll_group` is a real EHB/Luck input: outcomes in one group are mutually exclusive outcomes of one roll; groups are independent. New drops use `default`; existing groups (barrows-equipment, purple table, doom-1-16-aggregate, fortis-full-run-unique) are preserved. Only a Super Admin changes a roll group; Admins may add/edit `N x` rate text. Operator-reported counts are not agent verification.
- Updating a global catalogue entry never silently alters a published or historical board.

### Board and tiles

- `Board` states: DRAFT, VALIDATED, PUBLISHED, ARCHIVED. Only one board per event is active for competitive progress.
- The board draft exists from event creation and stays privately editable through signup and team preparation; event publication and signup opening neither need nor publish it.
- DRAFT reads derive names, artwork, rates and EHB from the current catalogue; cached totals are non-authoritative and invalidated by catalogue changes. The editor/preview uses the board-owned tile plus live catalogue and ignores projection fields.
- Validation requires every grid position to hold a valid tile. Any enabled Admin may approve. Approve board locks and version-checks the board and every referenced catalogue row, validates the grid, calculates all competitive values, writes a new immutable `BoardApprovalSnapshot` and sets it as the active pointer atomically; a conflict leaves no partial snapshot. VALIDATED means the complete board was validated, explicitly approved and snapshotted.
- Validated preview and publication read the active snapshot without recalculation. Unapproval or any competitive edit returns an unpublished VALIDATED board to DRAFT, clears the pointer, keeps the (superseded) snapshot and resumes live derivation. Draft finalization does not publish the board. Approval history is append-only; no reason is required while private.
- Approved/published tile, requirement, drop, rate, artwork and EHB snapshots are immutable to catalogue edits. A post-publication correction creates audited replacement values without rewriting the before-state.
- A tile (`TileTemplate`) is owned by exactly one board and never reused, copied or linked. Objective types DROP_REQUIREMENTS, MANUAL. Manual EHB is persisted in the tile-local `tile_templates.manual_ehb_override` and is required for manual objectives.
- `description_is_automatic`: a blank/whitespace edit stores an empty description with the flag true; nonblank text is stored trimmed with the flag false. This applies to working records only; snapshot text and mode are never rewritten.
- `BoardTile` places its tile at one zero-based row/column; move/swap changes positions and never duplicates. One board tile per position and one position per board tile. Nullable approval/publication projection snapshots are filled from the immutable snapshot at approval.
- `TileTemplateRequirement`: `target_contribution`, `duplicates_allowed`, `allow_higher_weightings`, manual fields. All active requirements must be complete for the tile to complete.
- Requirement bosses (`TemplateRequirementBoss`): a requirement may reference several activities; projection snapshots (boss name, efficient rate) are ignored while DRAFT and frozen at approval.
- Requirement drops (`TemplateRequirementDrop`): one eligible source-specific drop each, with an immutable `item_id_snapshot`; `credited_weight` defaults to 1 and the designer may set a higher value per drop; submitters cannot override the snapshot weight. While DRAFT `source_drop_id` joins the current catalogue; approval freezes item identity, names, rate mechanics and derived EHB.
- `BoardApprovalSnapshot` is the immutable version created by Approve board (version, approver/time, dimensions, calculation version, total EHB, `superseded_at`). Its child rows capture positions, name/description/artwork, `description_is_automatic`, requirement rules, activity names/rates, source drop with immutable item identity/name/rate/probability, caps/weights, manual EHB and derived tile/line/board EHB. Automatic description copy is materialized at approval and read only from the snapshot; derived text over the column limit rejects approval (no truncation); discarding a correction restores the prior mode and copy.

### Evidence and submissions

- `Submission` records event/team, tile/requirement, boss/activity, drop, credited player and playing account, credited weight, approved contribution (capped by remaining progress, Admin-confirmed), immutable server `submitted_at`, screenshot, optional note, status and feedback. `rejection_reason` is required when REJECTED. `expected_evidence_code` is an immutable snapshot of the code active at `submitted_at` (null when codes are disabled). The resubmission link is nullable and legacy, display only.
- `credited_weight` is copied from the selected immutable requirement-drop snapshot on create/retarget (default 1); neither submitter nor reviewer chooses it.
- Status PENDING, APPROVED, REJECTED, WITHDRAWN, REVERSED. Transitions: PENDING→APPROVED/REJECTED/WITHDRAWN; APPROVED→REVERSED.
- `EvidenceCode` history per event (code, `activates_at`, `retires_at` null for the final interval, creator, note): intervals can be scheduled ahead; adding one recalculates adjacent retirement boundaries; existing submissions keep their expected-code snapshot.
- `EvidenceAsset` roles ORIGINAL_EVIDENCE / REPLACEMENT_EVIDENCE.
- `ReviewAction` (actor, time, note, before/after snapshot); current actions EDIT_METADATA, APPROVE, REJECT, REVERSE_APPROVAL, WITHDRAW (`Resubmit` is retained in `ReviewActionType` for history).
- Drop-announcement tracking start is a persisted per-event boundary (feature deployment time for older events, creation time for new ones) combined with the membership join boundary; it is never initialized at first login, and earlier history stays untracked.

### Assets

- There is no generic asset entity: stored files are per-purpose records (`TeamImageAsset`, `BoardTileImageAsset`, `EvidenceAsset`) holding storage key, original filename, media type, size, checksum, dimensions, creator/uploader and owner. Evidence assets have stricter retention and access than decorative images.
- Application-owned images (team, custom tile artwork, evidence) are managed uploads referenced by asset id, never arbitrary URLs. Only catalogue `BossActivity`/`CatalogueItem` hold an external source image URL (cached locally); tile `ImageUrl`/`ImageUrlSnapshot` carry only that catalogue-derived artwork.

### Audit

- `AuditEntry`: optional event, actor, action, entity type/id, time, reason, before/after snapshot, safe request context.
- Audit writers stage the entry with the owning mutation or use `WriteAndSaveAsync`; standalone `WriteAsync` rejects a dirty context.

## 5. Calculations

- Official tile/team progress is reproducible from approved evidence contributions; reversal recalculates rather than relying on manual totals.
- Derived values (progress, rank) are distinguishable from authoritative records, and cached derived values are reproducible. `TeamTileProgress`/`TeamBoardProgress` may be computed or cached (per-requirement progress available for multi-requirement tiles); they are caches only, while evidence and board configuration stay authoritative.

### Contribution and progress

- `claimed = credited_weight`.
- `approved = min(claimed, remaining_requirement_progress, remaining_drop_cap)`, respecting the duplicate rule and the Admin-approved amount. Progress never exceeds the requirement target and never carries to another tile.
- Duplicates allowed: repeated approved drops count until the target or an explicit drop cap. Duplicates disabled: active contribution is capped per `(team_id, tile_requirement_id, item_id_snapshot)`, so each catalogue item has max contribution 1 per requirement even across several source drops (an explicit consistent max may override 1; missing max = 1). All source-drop aliases of an item in a requirement share that cap and must have the same effective max or board approval fails.
- Duplicate identity is the immutable shared catalogue item frozen in the event/approval drop snapshots, never the source drop, image, submission, current `SourceDrop` mapping or sibling capacity. Alternative sources for one item are valid. Frozen names are never rewritten.
- The same item may count in a sibling requirement independently; contribution, completion, reversal and rebalancing never cross `tile_requirement_id`. Retargeting Pending evidence recomputes the destination weight.
- `requirement_progress = sum(active approved contributions for requirement)`; `requirement_complete = requirement_progress >= target_contribution`.
- Drop tile: `tile_complete = every active requirement is complete`. Manual tile: `manual_progress = sum(active approved manual completion contributions)` (credited quantity normally 1), `tile_complete = manual_progress >= manual target_contribution`, which supports repeated objectives.
- Requirement completion time is the immutable `SubmittedAt` of the effective contribution that first reaches the target; `tile_completed_at` is the latest requirement completion time.
- `tile_completion_facts`: one row per event, team, board tile and approval snapshot for the current public approval generation, storing the tile time and JSON provenance of the qualifying requirement/contribution/submission identities and effective amounts. Approval and reversal/rebalance transactions reconcile affected rows from approved, non-reversed contributions; a replacement approval creates new-generation facts without deleting old ones; public reads never write facts.
- `row_complete(r)` / `column_complete(c)` = every board tile in that row/column is complete; diagonals are ignored. A completed tile counts once as a tile but in both its row and column; overlapping lines count independently.
- `board_complete = every board tile is complete`; `board_completed_at = latest tile_completed_at`. The first team by `board_completed_at` is the provisional winner; approval time never decides order.
- Approval or reversal recalculates requirement progress, tile, row, column and full-board completion, ranking/placement and player stats; Pending evidence never counts.
- Reversal: (1) mark the contribution inactive; (2) re-evaluate later approved evidence for the same requirement and raise previously capped contributions up to their original eligible claims; (3) record each automatic adjustment in review history; (4) recalculate requirement and tile; (5) row and column; (6) full-board completion; (7) reconcile the active-generation tile completion fact; (8) team placements; (9) the credited player's stats; (10) audit before/after values.

### Ranking

- `current_score_reached_at` = latest completion time among currently complete tiles in the active approval generation, null when none; it equals the board finish time when the board is complete. Retained `TeamCompletionCorrection` rows are historical and ignored by readiness and ranking; there is no manual time correction.
- The comparator is selected by the immutable `events.placement_rule` (both are implemented). New events use 1; pre-migration events and imports use 0. Provisional and final placements use the persisted value; saved official placements keep their rule, order and inputs.
- Rule 0 (`LegacyScoreTimeThenEhb`): finishers first, earliest board completion, completed lines desc, completed tiles desc, current-score time asc, credited EHB desc (full precision).
- Rule 1 (`CreditedEhbThenScoreTime`): board completion status, earliest board completion among finishers, completed lines desc, completed tiles desc, credited EHB desc, current-score time asc. Non-finishers compare `(completed_line_count, completed_tile_count, ehb_tiebreak_value, current_score_reached_at)`. Credited EHB is rounded to 4 decimals for both ordering and shared-rank equality (equal values fall through to time).
- Finishers rank ahead of all non-finishers, ordered by completion time. Teams with all competitive inputs equal (including the defined null-time rule) share the rank; there is no discretionary, name or identifier tiebreak, and team name is display order only.
- Placements are provisional while LIVE/AWAITING_FINAL_REVIEW. Finalization stores an `OfficialPlacementSnapshot` per team (place, board_complete/at, completed lines/tiles, `current_score_reached_at`, `ehb_tiebreak_value`, finalized_at, calculation snapshot).
- Unfinalizing never deletes the prior snapshot; re-finalization supersedes it. Historical official placements are never reranked or backfilled from current evidence; their nullable `current_score_reached_at` stays null when not recorded.

### EHB

- Simple estimate for item probability `p` and efficient rate `k` kills/hour: expected kills per drop = `1 / p`; expected hours per drop = `(1 / p) / k` (k = 100, p = 1/1000 → 10 EHB). For `q` interchangeable drops: `tile EHB = q × expected hours per qualifying drop`.
- Catalogue probabilities are final effective per-roll chances. Probability and completion rate are a reviewed pair under the same strategy, scale, difficulty, team and contribution assumptions: a personal in-name chance pairs with team completions/hour; a full-contribution chance pairs with completions per invested player-hour. Team size is never applied to both, and team-size/probability-scope context is never an input. Numerator fractions and `N x` rolls are explicit; raid/points/purple assumptions are resolved before entry. There are no boss- or raid-specific calculator rules.
- Complex estimate: model one completion at a time; drops in one roll group are mutually exclusive, separate groups independent, `rolls_per_completion` repeats the roll. Compute expected remaining person-hours per progress state, including credited weights, duplicate restrictions on shared identities and already-collected identities, choosing the most efficient available activity per state (alternative sources by lowest expected remaining person-hours). Separate objectives are computed independently and summed. A catalogue/drop tile is always auto-estimated.
- A missing or inconsistent probability, rate or source-drop assumption yields no automatic estimate and the drop tile fails board validation; nothing is guessed.
- DROP_REQUIREMENTS EHB derives from the live catalogue while DRAFT and from the approval snapshot once VALIDATED. An optional total tile override is allowed only on a valid calculated tile: the automatic baseline is retained, resettable and returned by the editor readback, clearing restores it, approval freezes the effective total. Overrides never bypass missing mechanics, change rates or rewrite approved/historical scoring. MANUAL needs an explicit manual EHB before approval. All requirements in a tile share one objective kind (a mixed edit is rejected without partial changes). Baseline and effective-value snapshots are preserved.
- The draft board reads catalogue names, images, rates and EHB mechanics live; catalogue writes invalidate derived projections and notify open editors; the server recalculates tile/line/total/per-player estimates from current rows and never trusts cached editor values.
- Every board tile stores the EHB estimate used at publication.
- `row_ehb`, `column_ehb`, `board_ehb` = sums of tile EHB snapshots; `line_spread_percent = (highest_line_ehb - lowest_line_ehb) / lowest_line_ehb × 100`; the editor warns when the spread exceeds the balancing target.
- Contribution EHB: `tile_target = sum(target_contribution of every requirement on the tile)`; `ehb_per_contribution = tile EHB snapshot / tile_target`; `submission_ehb_contribution = approved contribution × ehb_per_contribution`; `player_ehb_contribution` and `team_ehb_tiebreak` = sum of active approved submission EHB credited to the player/team. A completed tile credits exactly its EHB and a completed board exactly the board EHB; weight 2 earns two shares; standalone time-to-drop values for alternatives are never summed. It is an estimate of credited expected effort, not time played; it is the primary player ranking.

### Draft sizing and turn order

- Team count and sizes are derived, not stored: `team_count` = active included teams; participant total = confirmed internal participants available or already on drafted teams; larger size = `ceil(total / count)`, smaller = `floor(total / count)`, `larger_team_count = total mod count` (zero remainder = equal sizes). Captain/co-captain memberships count; non-included teams consume no turns. Planning team size is separate and stays editable after finalization.
- Before the first pick a balanced per-team turn/capacity plan is derived from the total, existing memberships and the randomized order; setup is invalid if preassignments make a maximum size difference of one impossible. A team above the smallest drafted-team count is ineligible until others catch up; the partial final round decides which teams get the larger size. The plan is not user-entered and cannot strand a confirmed included participant.
- Snake turn for overall pick index `p` and `N` teams: `round_index = floor(p / N)`, `position = p mod N`; even round → `order_index = position`, odd → `N - 1 - position`; the team at `initial_order[order_index]` picks.

### Derived views

- The Community Dashboard read boundary is `IAdminDashboardService.GetAsync(Guid, CancellationToken)` (alias `ICommunityDashboardService`) returning one `AdminDashboardResult` with stable EventIds, UTC dates, measured/unavailable metrics, EHB coverage and provisional state; event links go to `/Admin/Events/Manage/{id}`. It captures one request clock, confirms an enabled Admin/SuperAdmin and reads one repeatable-read snapshot.

- People = event participants plus memberships with valid `[JoinedAt, LeftAt)` intervals, excluding departures at/before actual start and joins at/after end; Live eligibility `JoinedAt <= requestClock` and `LeftAt > actualStart` (`LeftAt == requestClock` is still eligible). Zero-length/reversed intervals are rejected. Dedupe linked people by `(EventId, WebsiteAccountId)` and unlinked by `(EventId, ParticipantId)`; never by name/character guesses or signup status. Disabled accounts remain historical people; EmergencyCaptain accounts do not count.
- Approved submissions = distinct `SubmissionId` with active unreversed authoritative contributions, published approval requirements and matching event/team; reconstructed import contributions are excluded. A real set may measure zero; imported-only coverage without a later authoritative set is unavailable.

Board completion = snapshot-approved tile count / the immutable active published `BoardApproval` denominator (never working dimensions).
- EHB uses compatible stored event/competition/generation/fingerprint activity against expected Playing assignments over retained intervals → Complete / Partial / MeasuredZero; missing or incompatible coverage (including incompatible historical EHB) is Unavailable. No per-row current-roster projection, WOM fetch or signup-EHB substitution.
- Account metrics use the captured clock with strict boundaries excluding null/future values. New accounts are counted since the latest actually ended event (30 days only if no ended event exists); logins always over 30 days. An ended event with a missing/inverted actual boundary makes `NewWebsiteAccounts` unavailable with `Since` null (no 30-day fallback); an eligible event with missing/inverted dates keeps related aggregates unavailable.

- The Events directory adds no persistence. Live/past participation uses the Dashboard population mapper over valid retained membership intervals, including import provenance; a missing actual start/end (including pre-Live cancellation) is unavailable, never current confirmed signups or a fabricated zero; nullable capacity stays nullable. Directory reads use the same repeatable-read boundary and enabled-Admin check; hidden records need an enabled SuperAdmin and never enter ordinary directory populations or Dashboard totals.

Sync stops outside LIVE/AWAITING_FINAL_REVIEW with state retained and resumes only on a legitimate return to LIVE. Slots reconcile lazily to the anchored slot (a consumed slot is detected from the attempt time); there is no burst backfill after downtime; retries, manual and urgent refreshes never move the anchor.

### Luck

- Luck is a mid-rank percentile on 0–100: `100 × (P(X < received) + 0.5 × P(X = received))`, computed by the bounded distribution engine keeping bounded binomial distributions, conditional probabilities, reward rolls, mutual-exclusion roll groups, independent group convolution and numerical limits. No recentering; a deterministic sole outcome ranks 50; no activity, missing, impossible or unsupported inputs are unavailable.
- KC difference per playing character and boss metric, summed for the scope: `r / lambda - k` (`lambda` = deduplicated expected eligible outcomes per kill, `r` = approved outcomes, `k` = recorded KC). Each character/activity KC is subtracted once; repeated placements/outcomes never duplicate KC; independent roll groups contribute expected outcomes (not P(at least one)). Missing activity, zero/unsupported lambda, invalid mechanics and mixed unresolved attribution are unavailable. Totals are not adjusted for kill speed.
- Team/player and tile/team/contributor scopes keep separate aggregate and activity results. Tile Luck counts approved non-reversed item submissions for that tile and team (one item each, independent of weight); the expected count comes from the tile's distinct eligible item/source outcomes, the frozen first-approved event rates and full-event activity, aggregated over accounts. No percentage averaging, completion cutoff or re-division of raid rates; Stats and tiles share the calculation.
- Luck adds no per-objective cutoff when a tile completes (it assumes teams move on) and does not authorize submissions against completed tiles.
- Stats and selected-tile views use one saved Luck snapshot. A successful normal WOM sync is the calculation boundary: after accepting the response, approved non-reversed evidence is captured and all scopes are calculated inside the event lock/transaction and the lease, generation, source and assignment fences. Provider times stay authoritative. A candidate is published only after provider batch, evidence, competition/generation, assignment, source and lifecycle identities pass the transaction and lease fences; an oversized candidate is discarded with a diagnostic and the previous snapshot kept.
- Reads only project the saved snapshot (no fetch, recalculation, rescoring or timestamp rewrite). Approval, reversal and lifecycle transitions (Live → final review → archived) keep a compatible prior whole snapshot and its Last updated time; changed event, roster, competition, source or assignment identity makes it incompatible.
- A partial provider batch never mixes new activity rows with an old aggregate: a compatible prior complete snapshot is kept whole; with no prior, independently complete scopes may show while dependent aggregates are unavailable. Missing, unranked, estimated, zero-recorded, unsupported and bounded states stay distinct. A failed or skipped refresh keeps the last good result and never blocks publication.

### Item prices

- Prices come from the OSRS Wiki real-time API `https://prices.runescape.wiki/api/v1/osrs/` (`/mapping`, `/1h`) with the exact User-Agent header `DKLegacy - Community bingo item pricing - Discord: @chrisschmidt`. Provider success is cached 5 min and failures 30 s; Wiki timeout 15 s with one retry on 502/503/504.
- Event values freeze once at event start from the last completed hour: the midpoint of buy/sell averages rounded to the nearest GP (away from zero); one side if only one exists; otherwise the stored catalogue value. A missing price is not untradeable; manual/untradeable values survive refresh; the 0.5×–2× guard and zero↔positive flag apply (see §4 Stats and Luck persistence).
- An item introduced to an already-started event without a frozen value needs a stored catalogue value (0 is allowed, missing blocks), frozen at introduction with catalogue source and introduction time (never described as an event-start observation). No historical price fetch; existing snapshots never change.

## 6. Evidence visibility and finalization blockers

- Visibility derives from submission status and team access. Public: approved evidence metadata, credited player and screenshot. Captain/co-captain: all own-team submissions; other teams only via the public view (no other-team pending, rejected or withdrawn data). Participant: own pending/rejected/withdrawn including feedback; own pending edit/withdraw only while the window is open; approved via the public view; nothing of others' non-public state. Admin: complete evidence, metadata, prior versions, review actions and audit.
- A current team member sees the full retained team submission history, including departed teammates' records. Former members and cross-team viewers fail closed. The only former-member exception: after archive a former credited owner may read only their own Rejected/Withdrawn submission detail and asset via the account-history route.
- `/Evidence/{assetId}` derives status-aware visibility from the owning submission, with current team scope as the authority plus the exception above; no ledger, teammate, Pending/Reversed, mutation, review or cross-team access through it.
- There is no evidence-privacy request, player-hiding flag or hidden-but-approved state. To un-publish a screenshot an Admin reverses the approval with a reason; a corrected attempt is a new submission under the normal cutoff.
- Evidence eligibility derives from the append-only lifecycle transitions: the gap of an AWAITING_FINAL_REVIEW→LIVE resume stays ineligible, and review projections flag evidence in the gap without rewriting timestamps.
- Each transition into AWAITING_FINAL_REVIEW opens one immutable review cycle. Cycle-scoped records (legacy acknowledgements/corrections/resolutions, finalization snapshots) cannot authorize a later cycle; finalization snapshots retain the consumed resolution identities and calculation inputs/results.
- Mandatory finalization gates: uploads closed, zero Pending submissions, valid reproducible placements, plus current-event/lifecycle/version checks. There is no inspection, manual placement correction, tie acknowledgement or "Mark resolved anyway" bypass; legacy resolutions are history. Review mutations advance competitive freshness atomically. Normal finalization requires an explicit server-validated confirmation value (a browser confirm is only an enhancement).
- The finalization transaction rechecks gates and versions, calculates with the event's ranking rule, stores immutable official placements with actor/time/audit and transitions to ARCHIVED. There is no separate Archive action. Shared ranks need exact equality of all inputs.
- An optional WOM refresh failure never blocks publication. The typed `finalWomRefresh` status, skip reason and next-eligible time are stored in `calculation_inputs_json` (missing → "Not recorded"); reasons come from the actual lease-refusal branch; actor IDs/times are retained and usernames resolved for display; provider error text is not persisted; the eligibility time is informational.
- Prior official versions are never silently recomputed. At upload closure ordinary roles become historical and mutations stop; retained emergency identities never regain authority on reopening.

## 7. Concurrency and integrity

- Optimistic versions and event/team/participant locks reject stale writes; a stale write never overwrites a newer value. Identical repeats are safe where the journey declares idempotency.
- Operations in one database transaction: event draft creation (with audit and the actor-scoped creation operation); event discard/cleanup/tombstone audit; waiting-list promotion; draft pick/undo; submission approval; approval reversal; board approval snapshot; board publication from the active snapshot; finalization; unfinalization; hide/restore (with metadata, audit and visible-event projection invalidation).
- Atomic integrity rules: no double approval; concurrent reviewers cannot both apply (concurrency token or row lock); promotion never overfills capacity; no participant drafted twice; no tile in two positions and no position with two tiles; a captain cannot submit for another team; contribution stays within caps; no finalization with blockers; catalogue updates never rewrite snapshots; only `IncludedInDraft` teams get turns or affect sizes; assigned participants are excluded from the pool; hide/restore is atomic, hidden events are excluded from ordinary projections and Restore rewrites nothing.
- Current-event singleton: several SIGNUP_OPEN/SIGNUP_CLOSED events are allowed only with non-overlapping half-open `[event_starts_at, event_ends_at)` windows (touching allowed); LIVE/AWAITING_FINAL_REVIEW/FINALIZED are singleton. Every entry path (start, restore/unhide, reopen, imports, repairs) enforces it; hidden events are excluded; historical imports enter ARCHIVED; drafts reserve no window; cancelled/discarded/archived events never block. `is_development_fixture` is set only by the Development seeder, never by Admin input, and is ignored by the Production lifecycle.

### Events and signup

- Event creation: one Application contract plus an Infrastructure service; a transaction-scoped PostgreSQL advisory lock over the namespaced actor/request identity serializes retries and Check again; the composite PK enforces uniqueness; enabled Admin authority is rechecked; Web supplies the actor and renders errors. A lost-response commit is recovered by the retained key, never by auto-creating under another key.
- Event identity edits use original/intended/current canonical values: untouched fields take current; the intent applies when current equals original or already equals the intent; any other same-field change blocks the save until resolved against the reviewed current value, rechecked inside the Serializable transaction. Failure keeps drafts and baselines; legacy requests without complete baselines fail closed. Timezone confirmation also compares the timeline-consequence fingerprint (UTC at PostgreSQL microsecond precision); schedule-only changes need a fresh review. No new persistence or receipts.
- Signup-form definition edits (field add, custom edit, account rename, move, co-captain enable) submit the rendered `SignupForm.version` as `expectedFormVersion`; missing/malformed values fail closed and stale ones are rejected under the event lock before writes. Delete/disable keep question-version plus impact-count confirmation. Settings results keep the submitted version separate from the current saved version, capacity, waiting state and code-required/code-present flags; code values/hashes are never returned; capacity and code save in separate transactions. Saves return authoritative values and the resulting event version; there is no whole-page atomic save and no per-question public/private toggle.
- The null→first `FirstResponseAt` transition alone does not advance the form version; a simultaneous definition/settings change or explicit version advance still does; there is no stale bypass; guards are rechecked under the Serializable event lock. A required custom field added after the first response succeeds as optional with a `CompletedAsOptional` outcome and explanation (no rejection, no backfill).
- Field creation idempotency: the add carries a nonempty request id bound to Admin, event, normalized definition and original form version. Handlers forward actor, request id and submitted form version; the operation row records the fingerprint and created id in the Serializable event-lock transaction. Replay is resolved after authorization but before stale/lifecycle gates: an identical retry returns the created field id with no new definition, audit or version change; a reused id with changed intent/actor/event fails closed without disclosure; a deleted field is reported removed, never recreated. Replay/readback uses the request identity plus the linked immutable creation audit; missing/corrupt audit fails closed. Three bounded retries, then an explicit retryable result; an uncertain commit propagates. Fingerprints contain no clock or round-tripped timestamps. A new request needs the current baseline and pre-draft authority, rechecked on each attempt. Only the Questions default/AddAccount POSTs bypass the generic lifecycle filter.
- Selected confirmation, selected override restore and selected override Add serialize on authoritative capacity/participant state. A full-event override adds exactly one place and consumes it for that participant in the same transaction; ordinary capacity-increase promotion is unchanged; a retried/stale intent never double-increments capacity or duplicates audit/notifications.
- Withdrawal, rejoin, restoration, reservation changes, status assignment and promotion are atomic; restore/rejoin reacquire every required reservation or fail without partial state. Participant and Admin withdrawal share WITHDRAWN; the actor is recorded via `withdrawn_by_account_id` plus transition history.

### Notifications and approvals

- Required notifications are written within their accepted mutation. Retry-sensitive producers (historical withdrawal/replacement, evidence rejection) and scheduled attempts use deterministic IDs/deduplicate per owning transition/occurrence and recipient; other notifications may use fresh GUIDs; there is no universal dedupe rule.
- Approval records immutable completion-at-approval metadata and an event-scoped ordinal inside the serialized approval transaction; queue snapshots use the committed ordinal boundary so bulk dismissal and paging keep later arrivals. Progress is still derived from evidence.

### Boards and draft

- Each board aggregate has an optimistic version covering tiles, requirements, layout and publication state; every mutation sends the loaded version; a stale write returns a recoverable conflict without overwriting.
- Approval locks/version-checks every referenced board and catalogue row and fails atomically on a concurrent edit. The active pointer identifies the frozen version for preview/publication; unapproval/editing clears it and marks the snapshot superseded (never deleted); publication points to the active snapshot and never recalculates.
- `BoardRequirementDropSnapshot` rows referenced by an immutable approval are retained even after the private working requirements/tiles are removed. Rules and weights come from the approval tree, not the catalogue or cached values. Resolution uses only the exact `RequirementId + SourceDropId + ItemId` within the authorized event/board/approval; missing/ambiguous matches fail closed (no guessing, recreating or first-match). Retention never makes removed objectives current or visible. Substantive replacements never reuse an approved identity; wording-only edits keep it. Correction, submission and publication paths use consistent transaction/lock ordering; current submissions use the active published contract.
- Renewable board-editor lease: opening does not acquire it; explicit edit, release or confirmed takeover change ownership; viewers get live updates; navigating away sends a keepalive release; activity renews at a throttled interval; 5-minute inactivity expiry is the fallback.
- The draft session has an active-controller lease (Admin account plus lease/version) checked for start, pick, undo, zero-pick cancel and finalize; there is no Pause/Resume; observers are read-only; a confirmed takeover atomically replaces the lease with an audit entry. Draft-pick transactions keep serializable isolation and uniqueness constraints as the final integrity boundary under racing/retried requests.
- Readbacks for Review, Board and Teams are authorized, no-store Repeatable Read projections reusing allocation, leases, snapshots, versions and immutable pick/member identities; no request receipts or replay; a current-state match never identifies the causing actor; unavailable stays unknown. Review exposes nullable before/after versions and the credited participant's team-leave time; Board compares the full publish projection including frozen names/rates and keeps distinct snapshot ids for publish vs discard; Teams separates roster `PublishedAt` from WOM operation times.
- PageModel mutations rely on the per-request cookie recheck; that recheck is not persisted authorization.

### Wise Old Man and Stats

- WOM lease acquisition and HTTP never share a transaction. Publication happens only while LIVE/AWAITING_FINAL_REVIEW and while competition id, lease owner and assignment fingerprint still match. A later complete or partial generation is authoritative (older rows retained). Missing expected accounts get no row (never zero, never carry-forward); partial projections show totals plus coverage when ≥ 1 account matches; zero matches show no rankings.
- Durable WOM management operations keep only operation id/type, actor/origin, immutable desired fingerprint/payload reference, phase, remote id/receipt, safe error code, and retry/outcome times. PostgreSQL uniqueness/conditional claims serialize per event/link across requests and workers; expired Sending claims become Unknown and never authorize a blind duplicate Create/Delete; pending updates survive restart and coalesce to the newest revision. Remote management never deletes local team, membership, assignment or evidence history.
- Stats reads use one Repeatable Read (or Serializable) snapshot per response. Checkpoint writes lock the event, require the exact current evidence/activity/source/assignment/lifecycle key and reject older revisions/calculation times. Frozen item prices, first-approved rate identities and official placements survive transitions.

## 8. Object storage

- R2 stores original evidence screenshots, team images, custom tile artwork and locally managed boss/item images. Historical replacement/Admin attachment objects are readable only for retained history; there is no active Admin evidence-upload or replacement workflow.
- R2 is accessed through an application-owned storage interface over the S3 API; provider code lives only in Infrastructure.
- Uploads stream through the application to R2, so authorization, size, media type and checksum are enforced in one place. The server validates, inspects, checksums, stores and authorizes each asset under its retention/privacy rule; invalid type/size/content or a storage failure keeps the prior asset with retryable feedback.
- Upload protections: configurable maximum size, allowed media types, image decode validation, generated keys, original filename only as metadata, checksum, no public bucket listing, evidence served via authorized routes or time-limited URLs.
- All participant/Admin images use managed upload via the shared asset storage, never arbitrary external URLs. Team images and custom tile artwork reuse the evidence upload interaction with decorative authorization and retention, independent of evidence retention.
- External image-source URLs are accepted only for global catalogue bosses/activities and items, fetched, validated and cached through the catalogue-image path; no other form has an image-URL field.
- Catalogue artwork keeps its OSRS Wiki source URL in the database and is served through a same-origin cache, filled on demand or by `--sync-catalogue-images`: misses coalesce; one process-wide fetch at a time with ≥ 500 ms between starts; provider pauses are honoured; successes are kept; failures get a bounded negative cooldown; HTTPS Wiki allowlist; media-type/size validation. Location `CatalogueImageCache:LocalPath` (git-ignored in development, a persistent volume in production). No client hotlinking. The cache is rebuildable and not backed up.

## 9. Authentication and authorization

### Authentication

- Secure cookie authentication. One website account with public username and password plus optional Discord. Account creation starts with Discord; onboarding requires username and password before signup; Discord may be unlinked afterwards. Passwords use the ASP.NET Core Identity hasher and are never logged.
- Discord OAuth configuration is a deployment prerequisite, not an event setting. Signup readiness checks that the login path is configured/enabled without a live Discord API call; provider outages are handled at authentication time with retry feedback and no lifecycle mutation.
- Account types: the normal account (global `USER`/`ADMIN`/`SUPER_ADMIN`, optional Discord) and the retained emergency captain type, kept for history only (its authentication and authority are rejected). No Discord guild requirement. Authorization never depends on display or OSRS names.
- Passwords: at least 10 characters, printable/passphrases up to 200, no composition or periodic-change rule. Login failures disclose nothing specific; per-identifier and per-network rate limits apply.
- Cookies: non-persistent = browser session with a 12-hour maximum ticket; Remember me = persistent with a 30-day absolute maximum that sliding cannot extend; a separate external OAuth cookie handles correlation; onboarding state expires after 15 minutes and creates no partial database account.
- Disabled accounts cannot authenticate. Sessions carry `authorization_version` (and password sessions also `password_version`) and fail on mismatch, so invalidation takes effect without waiting for cookie expiry. A role grant/revoke increments `authorization_version`; revoking ADMIN→USER does not disable the account or touch event records; role history is automatic with no reason. A password change/reset increments `password_version`, ending prior password sessions but not separate Discord sessions.
- Password tokens: only hashes of random tokens are stored; purpose-bound and single-use; they expire 60 min after creation and are valid only unexpired and not superseded; a new token supersedes all unused prior ones. Completion updates the hash and changed time, increments `password_version`, consumes the token and records history. Emergency setup/reset tokens and tokens targeting emergency accounts are rejected without being consumed. No reason is needed.
- Every Discord link mutation requires fresh current-password verification; LINK/REPLACE need completed OAuth for an unattached Discord id; the account update and transition commit in one transaction. UNLINK may leave no Discord; REPLACE never exposes an unlinked intermediate state. Each increments `authorization_version`, invalidates other sessions and never changes participants, links, roles, evidence or history.

### Roles and policies

- `RequireAdmin`/`RequireSuperAdmin` check the global role, independent of Discord state. Exactly one active SUPER_ADMIN: a partial unique constraint enforces at most one; controlled setup/bootstrap and the ownership-transfer transaction ensure one exists. Ownership transfer atomically locks both accounts (destination → Super Admin, source → Admin). Signup/onboarding and public login never assign privileged roles; emergency accounts have no global role and cannot be promoted.
- Policies: Admin-only event/catalogue management; participants act on their own record/submissions; captain/co-captain rights come from the team roster role; drafted-team captains see the expanded signup projection only before finalization; role management and ownership transfer are Super Admin only; emergency commands are unregistered. Authorization is checked on every mutation; hidden controls are not security.
- Only an active membership may hold a current captain/co-captain role; withdrawal appends the revocation atomically. Role authorization resolves from the latest transition and current membership, never an OSRS character or a stale credential.
- Captain authorization requires an active normal website account, participant ownership plus current Captain/Co-captain membership for the event/team, a visible event, the submission team equal to the current membership, and an event state/upload window that permits the mutation.
- Team focus: membership grants read, the team's captain/co-captain grants mutation; ordinary ADMIN cannot read. A Super Admin may read another team only after explicitly enabling team-scoped read-only inspection (visible, session-limited, not persisted) before cross-team reads/subscriptions, and never mutates. Focus target fields are exclusive per kind and `(team_id, target_kind, target identity)` is unique. Default responses contain no cross-team focus data; invalidations are team-scoped.

### Hidden events

- Visible-event queries and guards explicitly require `is_hidden = false` (no global EF query filter) for public, participant, Captain, Admin, notification, action, audit, evidence and realtime projections.
- Hidden events appear only in the Super Admin Hidden area of Events Control with a limited Manage view (lifecycle data, hide/restore audit, Restore), reusing `RequireSuperAdmin` (no new policy, route, page or table). Every other workspace, public route, history, evidence, notification and realtime path returns 404/absent, including for Super Admins. All data is retained.

## 10. Scheduled behaviour

- One in-process background service runs short idempotent checks: scheduled signup open/close, scheduled start via the readiness policy, LIVE → AWAITING_FINAL_REVIEW at end, close submissions at cutoff, waiting-list promotion fallback, cache reconciliation. Timestamps are authoritative, so the effective state is derived correctly after downtime.
- One typed WOM v2 client (contactable User-Agent, optional API key, bounded timeout, structured logs) with one process-wide serialized limiter (single replica): one bootstrap request after restart; a ≥ 60 s fail-closed pause on missing headers or transport failure; it observes limit/remaining/reset, reserves the last three requests and rejects manual requests locally before exhaustion. Automatic cycles make 1 attempt + 3 retries with separate due times.
- Competition sync is a separate hosted worker: it takes a fenced lease in a short transaction, does HTTP after commit, and publishes in a second transaction rechecking Live, competition, lease, fingerprint and cooldown. It maps to every unreleased `PLAYING` assignment with a per-character generation and completeness/error; a partial result publishes matched rows only (no zero/carry-forward); a zero-match partial has no rankings. Projections read only the PostgreSQL cache, labelled **Fetched from Wise Old Man**. No Redis, broker, distributed limiter or second replica.
- Admin WOM writes use a separate typed management service and worker. Domain/Application own finalized-draft eligibility, name normalization, roster projection, empty-team rejection, the 50/30 name limits and the `actual_started_at` boundary; Infrastructure owns the POST/PUT/DELETE adapter, errors, Data Protection code protection, operation claims and receipts. The worker never holds a transaction across HTTP and never calls statistics polling or `update-all`.
- Error classes: 5xx, timeouts, network errors, 408 and 429 are temporary; named 400s, missing/invalid code, 401/403/404 and validation errors are permanent (sanitized codes). An unknown end-only write is read back: target window present = done, unchanged = resend on schedule, unavailable = spaced reconciliation. A new target resets attempts; an old target's late failure is historical.
- Create sends one full team payload and persists the link plus a protected receipt; an unknown Create outcome is durable and stops auto-retry; a local persistence failure re-saves the same receipt. Updates coalesce and revalidate. After Live only reconciliation and the date-only end update run (no roster changes or delete). ID-only links stay read-only until protected-code adoption and never carry deletion authority. Replace/disconnect retires the credential under operation guards; a Sending/Unknown Create blocks linking; renames are not supported; My Accounts never rewrites frozen identity.

## 11. Realtime

- SignalR sends small invalidation/update messages after approval/reversal, tile/board completion, catalogue changes affecting an open draft-board editor, draft picks and event state changes. Hide/restore emits only an authorized Events Control invalidation (no personal notification, never hidden data). Messages carry no authoritative or secret data and never replace transactions; approval/finalization invalidations are emitted after commit.
- SignalR/fetch updates are invalidations only: they never replace authoritative state or interrupt an active submission or submission-result acknowledgement. Reconnect and navigation reconcile against PostgreSQL.
- Participant announcements reuse the generic SignalR invalidation connection; personalized state comes from authenticated announcement endpoints enforcing account/event membership; nothing private is broadcast to public groups; mutations use anti-forgery. Announcements add no idle polling, recipient fan-out, extra realtime service or scheduled job; the existing 100-viewer capacity evidence stands, with no extra load-test gate; performance is reassessed from observed behaviour.
- Realtime refresh uses bounded targeted queries, coalesces approval bursts and never reloads the page or redraws an active board/submission workspace; the Drops feed refreshes affected entries preserving filters, scroll and an open popup.
- The site stays usable without realtime; a normal refresh retrieves authoritative state.

## 12. Security baseline

- Caddy HTTPS; secure, HTTP-only, same-site cookies; CSRF protection; CSP; server-side authorization policies; login/signup rate limits; upload validation; parameterized EF access; secrets outside source control; no public PostgreSQL; minimal container privileges; regular OS/image updates; audit of competitive and privileged actions. Admin two-factor authentication is not implemented and remains an optional future evaluation.
- Logs never contain passwords, signup edit tokens, storage credentials or full private evidence URLs. Audit snapshots never store password hashes, edit tokens or other authentication secrets.

## 13. Portability

- The app can move to another VPS, Render, Railway, Azure Container Apps or any container host with PostgreSQL and S3-compatible storage. This is preserved by a standard container image, standard schema/migrations, Npgsql without provider-specific features unless justified, the S3 storage interface, no Hetzner-specific logic, environment/secret configuration and reproducible bootstrap instructions.
- Moving hosts = deploy the container, restore/connect PostgreSQL, configure R2 credentials, update DNS.
