## Required reference corrections

**A1 — P1: a reset secret can be displayed under the wrong account after pending navigation.** `Accounts.dc.html:572–576,610–616,677–694,845`. Generate a reset link for A; the browser Back/Reload path bypasses drawer `busy`, allowing another drawer B before completion. Callback calls current `updDr` and stores A's link with `forId=A`, but `vmDr` ignores forId and labels it with B's username. Consequence: the Admin could hand A's credential to B. Smallest correction: bind every async response to captured account/operation identity, verify `link.forId === drawer.id` before rendering/copying, and guard pending in-page navigation/close. Clear discarded secrets and never move them into a replacement drawer. Apply the same context guard to role/status readback, confirmations and transfer completions. Browser-level interruption must leave explicit uncertainty rather than let a late response recreate a result in another context. This is a reference defect, not evidence that production's target-checked TempData has the same flaw.

**A2 — P2: uncertain readback overstates both success and no-change.** `Accounts.dc.html:661,668–673,735–740`. Role/status recovery tests only current role/active plus a changed version, so another admin's matching action is attributed to this request; an intervening reversal is called “It wasn't changed.” Transfer checks only whether the selected recipient is now owner; if transfer happened then ownership moved again, it says “You're still the Super Admin. Nothing changed,” without checking the actor or current owner. Disable recovery also lost the original reason, so it cannot reconcile reason/actor. Smallest correction: retain full intended operation/baseline, report current role/state/owner and relevant available history, and do not assert attribution or historical no-change without evidence. Preserve unresolved state on read failure; gate repeat/conflicting actions until reconciliation or an explicit informed leave. Current-state readback is not permission to replay.

**A3 — P2: dirty disable reasons are silently discarded.** `Accounts.dc.html:623–625,652–660,853,866`. Cancel/Escape/backdrop/Back close a typed disable reason directly; stale refusal closes the dialog and drops it rather than retaining intended and current values. Smallest correction: use the shared discard choice for unsent reason text and preserve a stale draft while showing current authoritative data. Transfer recipient selection is also unsaved work (`706–714`): closing should protect that intent while continuing to clear password on completed close/Back. Do not preserve secrets in history or add confirmation to an unchanged dialog. UI_SYSTEM 657–666 already defines this policy.

**A4 — P2: direct-link load recovery loses the requested drawer, and filtered-out targets lose return focus.** `Accounts.dc.html:567–569,581–586,917` loses the route callback on Try again. An account direct link that fails once then succeeds leaves `account=` in the URL without its drawer. `611–616` returns focus only to the original row or the same row ID; after granting a User under the User filter, that row disappears and shared `restoreFocus` has no surviving fallback (`ui/behavior.js:55–61`). Smallest correction: resolve the current route after successful retry, retain filters/history/scroll, and fall back to a stable directory heading/search control when the originating row is gone. Missing targets must remain explicit, not another account.

**A5 — P2: revoking a disabled Admin falsely says the account stays active.** `Accounts.dc.html:541,838,857–859`. The supplied disabled Admin `ember_bo` is eligible for revoke, which correctly leaves `active=false`; confirmation says “The account stays active.” Smallest correction: describe actual retained status (“stays disabled” here, or “status is unchanged”) in both row and confirmation. Role revocation must never imply restoration or mutate status. Production revoke (`AccountAdministrationService:24–31`) intentionally changes only the role.

**A6 — P2: transfer captures the destination version too late to protect the confirmation.** `Accounts.dc.html:710–724,872–884`. Destination version is fetched from current server state when Submit is pressed, rather than captured with the selected/rendered account. The displayed before-role also comes from live `srv()`. A changed destination can therefore bypass the stale check and rewrite the confirmation's basis. Smallest correction: store selected destination identity/version and before-role with the confirmation, submit that immutable baseline, and reconcile stale/disabled/lost-owner outcomes using current data. Production already carries the rendered option's authorization version (`Transfer.cshtml.cs:58–65`; `account-transfer.js:5–9`) and rechecks it atomically. Do not refresh the baseline silently just before sending.

**A7 — P2: directory search is case-sensitive against stored usernames.** `Accounts.dc.html:591–594` lowercases the query but not `a.username`; mixed-case valid usernames disappear for matching lowercase searches. Production searches NormalizedPublicUsername (`Index.cshtml.cs:34–37`). Smallest correction: normalize both consistently and keep the rendered query, URL and 100-character limit synchronized (the retained qDraft at799 otherwise can filter with more text than the URL stores). Full positive-integer page validation/canonicalization belongs in the same route integration; `parseInt` currently accepts junk suffixes.

**A8 — P2: header-opened Transfer leaves the background scrollable.** `Accounts.dc.html:911` locks for drawer/mobile navigation only. Transfer opened from the directory header has `S.tm` with no drawer, so the existing scroller remains unlocked. Smallest correction: include active transfer/confirmation modal state in the existing scroll lock, preserving focus trap, Cancel entry focus and post-transfer sign-in state. Source finding only, not visual acceptance.

Additional small correctness notes within the above work: ordinary Back calls `closeTm` directly (`571,709`), bypassing the done/unsure layer's Escape policy (`875`); keep one consistent explicit-leave/sign-in route.
