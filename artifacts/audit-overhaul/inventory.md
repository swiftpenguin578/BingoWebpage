# Audit overhaul — item 0 inventory (brief 147)

Read-only inventory of every recorded audit action key: where it is written, what it stores, what the Audit page shows today, the proposed readable text and the affected account. **No production code was changed.** For approval by the user before item 1.

## How this was made

- **Key list:** the same rule as `AuditLabelCompletenessTests` (string literals with an audit prefix in `src/`, minus the 7 validation operation names, plus the 2 composed `.wom_sync` keys; the two composed Discord keys are found as literals in `AuditPresenter`). Result: **168 keys = 168 rows** below. The test only asserts “> 150”.
- **Producer:** `file:line` of each write in branch `audit-overhaul` at `82262aed`. Keys with no current producer are marked *Retired* (with the commit that removed the producer, from `git log -S`), *Label only*, *Review history only* or *Notification type only*.
- **Today:** rendered by the real `AuditPresenter.Present` (English `en-GB`, Danish `da-DK`) from synthetic entries shaped exactly like each producer's stored payload (same anonymous types/serializer, so enum numbers etc. are real). Harness was a scratch console project outside the worktree, not committed. Danish column shows the Danish action label, target and first changes; field names and Context text are mostly untranslated today (e.g. `Event starts at`, `Payment changed.`), which applies to every row.
- Row today = action label (link) + record line; drawer = Record, Reason/Context, Changes, Technical details. Identifiers that are GUIDs are never shown except inside Technical details or free text.
- **Proposed:** one sentence “who did what to whom”. Placeholders: `{actor}` = the acting username (or “System”/automatic phrasing when there is no actor), `{account}` = website username, `{player}` = participant's character (OSRS) name, `{team}`, `{event}`, `{board}`, `{tile}`, `{boss}`, `{item}`, `{question}`, `{before}`/`{after}` = readable values. Names are resolved at display time in one batch per page; when the target is gone the stored name/label is used, else the id. The **Changes** table stays and gets readable values (enum names instead of numbers, names instead of ids, no duplicate/technical rows).
- **Affected account:** **W** = website account (username), **P** = playing (OSRS) account. “—” = none. ⚠ = cannot be derived reliably (explained in the cell).

## Cross-cutting findings (affect several rows)

1. **Status entries show no changes today.** `SignupService.AddAudit` (src/Bingo.Infrastructure/Signups/SignupService.cs:2944) stores Before/After as bare strings (`"Confirmed"`), not JSON, so promoted/confirmed/moved-to-waiting/rejoined/restored/withdrawn show “No field changes”. Item 1 must read these as a status pair at display time (stored data unchanged).
2. **Enum numbers.** Event lifecycle `state` and submission `Status` are serialized as numbers (`State: 3 → 4`, `Status: 1 → 2`). Map to names (Signups closed → Live; Pending → Approved).
3. **No event id on several Teams/Draft entries.** `Draft.cshtml.cs` uses the 7-argument `WriteAndSaveAsync` / `Audit` helper for `team.created`, `team.member_added/removed/moved`, `draft.cancelled`, `draft.finalized` (and the finalized-roster correction path). These rows show “No event” and are missed by the event filter. Display can derive the event from the team/membership/draft (stored data unchanged) — see Q6.
4. **Target types without a label:** `pick` (draft picks) and `promotion_follow_up` (retired) render as “Recorded target”. `draft_publication` rows actually carry a **membership id** (or team id for the retired preformed correction).
5. **Masking is broad.** Any key containing `code`/`password`/`credential` is fully withheld, including non-secret facts (`event.evidence_code_mode` “Enabled”, competition credential outcome text). The brief protects masking as is — see Q5.
6. **Not audit actions:** `participant.accounts_changed`, `participant.prelive_withdrawn`, `participant.restored`, `participant.waiting` exist only as notification types; `logout` **is** written to the audit (`src/Bingo.Web/Pages/Account/Logout.cshtml.cs:20`) but has no audit prefix, so the completeness test does not see it and it renders as “Recorded administrative action” — see Q7.
7. **Danish terminology is mixed** in `AuditResource.da.resx` (“Begivenhed …” vs “Event …”, “Plade”, “Dokumentation”) while the rest of the site mostly uses “event”, “board”/“plade” and “bevis”. `event.finalized` and `event.ended` share the Danish label “Begivenhed afsluttet”. Proposed Danish below uses **event / board / bevis** — see Q1.

Proposed fallback order at display time: stored published name → `Details.participantBefore.activePlayingAssignments[0].DisplayName` (stored character name) → the participant's current primary character name (batched lookup) → the membership id. Applies to `roster.finalized_added` too.

## Open questions for the user (decided 10 October 2026 — see “User decisions and implementation” at the end)

- **Q1 — Danish terms.** The audit's Danish labels mix “Begivenhed/Event”, “Plade/Board”, “Dokumentation/Bevis”. - **Q2 — Where the sentence appears.** Options: (a) the sentence replaces the action label in the list row and the drawer title (label stays only in the Action filter); (b) the label stays as the row/drawer title and the sentence is a new line under it (list sub-line and drawer Summary); (c) sentence in the drawer only. **Recommendation: (b)** — keeps the approved layout and the filter vocabulary, and the sentence replaces today's record line (“Participant”) without adding a row.
- **Q3 — Entries affecting several people** (`draft.team_removed`, `team.inclusion_changed`, `event.signup_administration_updated`, `participant.prelive/live_replaced`, `participant.ownership_transferred`). - **Q4 — Owner at the time vs now.** Participant entries store only the participant id; the website account and main character are resolved **now**, so after an ownership transfer or a main-account switch the column shows the current owner/character, not the one at the time. Options: (a) accept and say so in the drawer (“current owner”); (b) show “—” when it may have changed (not detectable cheaply); (c) start storing the owner in new entries (changes what producers store — outside this brief's protection). **Recommendation: (a)**.

Options: (a) keep masking exactly and use sentences without values (“changed the signup code settings”); (b) allow these named keys to show the non-secret fields. **Recommendation: (a)** in this brief (as protected); record (b) as a backlog item if wanted.
- **Q6 — Rows without an event id** (finding 3). - **Q8 — B2 cap.** Options: (a) 25 ids + count (worst case 2,132 chars); (b) 50 ids + count (worst case ~3,100 chars); (c) count only, no ids. **Recommendation: (a)**; drawer shows up to 10 names then “and N more”.
- **Q9 — Self-actions.** For `account.username_changed`, `password_changed`, `discord_*`, `onboarded`, `participant.withdrawn`, `participant.rejoined` the actor is the affected account. ## User decisions and implementation (10 October 2026)

The user approved this inventory with decisions A1–A10 (brief 147, “User decisions on the inventory”). Where a decision changed a proposed text, the implemented behaviour is:

- **A1 (Q1 a):** Danish audit texts use *event / board / bevis*; existing audit labels were relabelled (e.g. “Begivenhed startet” → “Event startet”, “Plade offentliggjort” → “Board offentliggjort”, “Dokumentation godkendt” → “Bevis godkendt”); `event.finalized` is now “Event færdiggjort” (no longer equal to `event.ended`).
- **A2 (Q2):** the action label stays the row/drawer title; the sentence replaces the record line under it in the list and is shown at the top of the drawer summary. The drawer “Record” row keeps “type · name” (now with resolved names).
- **A3 (user, replaces the Q3 proposal):** one affected account → it is shown in the column; more than one → the column says **“Multiple accounts” / “Flere konti”** and the drawer lists all of them (at most 10, then “and N more” / “og N mere”, A8). This applies to every multi-account row above (team removal, inclusion change, cap change, replacements, ownership transfer).
- **A4:** an owner or character looked up at display time is marked “(current owner)” / “(nuværende ejer)” in the drawer.
- **A5:** masking unchanged; the masked actions get sentences without values (“changed the signup code settings of {event}”). Showing their safe values is the backlog row “Audit: show safe values of "code" settings”.
- **A6:** entries stored without an event show the event derived from their team, membership or draft (display only; the event filter still uses the stored event id).
- **A7:** `logout` → “Signed out” / “Logget ud” (sentence “{actor} signed out.”), in the Accounts area and in the label completeness test.
- **A8:** new `draft.team_removed` entries store `EndedMembershipCount` and at most 25 `EndedMembershipIds` (+ `EndedMembershipIdsOmitted`); worst case about 2,200 characters. Older entries (full list) display the same way.
- **A9:** the Affected account column is filled even when it is the actor's own account.
- **A10:** automatic entries use passive sentences.
- **B3:** fallback order as proposed: stored published name → stored character name (`participantBefore.activePlayingAssignments`) → the participant's current character → the membership id.

**Final wording** lives in `src/Bingo.Web/UI/AuditSentences.cs` (English formats) and `src/Bingo.Web/Resources/AuditResource.da.resx` (Danish); `AuditSentenceTests` checks that every format has a Danish entry with the same placeholders. Small wording differences from the proposals above: payment reads “marked {player} as paid/unpaid”; start/signup-opening blockers are counted (“1 start blocker(s) were open”) instead of named (codes stay in Technical details); tile positions read “row r, column c”; board names are quoted; the main-account switch reads “made {new} the main account instead of {old}”; the review-only submission actions (Review page history) got sentences too; notification-only keys (`participant.accounts_changed`, `prelive_withdrawn`, `restored`, `waiting`) have no sentence.
